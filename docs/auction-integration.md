# Интеграция активных лотов RU

Дата проверки: 2026-10-24. Основание: контракт §4/§7 подготовительного отчёта,
официальный OpenAPI `https://eapi.stalcraft.net/openapi` (актуальное имя STALZONE,
production `https://eapi.stalzone.com/`) и отдельные реальные production-запросы.

## Внешний контракт и наблюдения

OAuth: `POST https://exbo.net/oauth/token`, form-urlencoded:
`client_id`, `client_secret`, `grant_type=client_credentials`, обязательное
пустое `scope=`. Ответ: `access_token`, `token_type=Bearer`, `expires_in`.
Проверен настоящий успешный ответ с переданными пользователем серверными
реквизитами; значения секрета/токена в документацию и журналы не включены.

Лоты: `GET https://eapi.stalzone.com/RU/auction/{id}/lots`, Bearer только с сервера.
Запрашиваются `offset`, `limit`, фиксированные `sort=buyout_price`, `order=asc`,
`additional=false`. Этот внешний порядок фиксирован; клиентские фильтры и
сортировка загруженных лотов не меняют внешние параметры или пагинацию.
Все страницы запрашиваются по возрастанию общего выкупа. Это запрошенный порядок
источника; известные ограничения соблюдения параметров внешним API сохраняются.

Фактический ответ: `{ total, lots }`. Строка содержит `itemId`, `amount`,
`startPrice`, `buyoutPrice`, `startTime`, `endTime`, `additional`; `currentPrice`
может отсутствовать. В просмотренных ответах он отсутствовал. Стабильного ID
именно лота в схеме и просмотренных ответах нет. `additional` с характеристиками
не интерпретируется как идентификатор и не передаётся в DTO.

Подтверждено реальными запросами, **без подмены HTTP**:

| Предмет RU | Результат на момент проверки |
| --- | --- |
| `3g6p5`, Костюм «Штрих» | HTTP 200, один лот; браузерный сценарий поиска → выбор → таблица/карточка |
| `0r2qk`, «Highest power» | HTTP 200, total=0, lots=[]; в браузере «Лотов нет» |
| `3g1qz`, Водка | HTTP 200, 17 строк |
| `vjr1n`, АК-74М | HTTP 200, одна строка |
| `04yr`, Виток | HTTP 200, 55 строк при limit=20; offset=20 вернул те же 55 строк |
| `0r211`, Crye Precision SIX12 | HTTP 200, пустой список |

Пример нормализованного живого лота `3g6p5`: quantity=1, startPrice=`"0"`,
buyoutPrice=`"55555555"`, currentPrice=null, startTime=`2026-10-23T00:57:14Z`,
endTime=`2026-10-25T00:57:14Z`. Это историческое наблюдение, не константа приложения.

### Выявленные ограничения

1. **Пагинация источника расходится с OpenAPI.** В проверке `04yr` параметры
   limit/offset не ограничили и не сдвинули массив. Адаптер сохраняет все строки
   ответа; `nextOffset = offset + lots.length`, продолжение только при непустой
   странице и nextOffset < total. При полном массиве hasMore=false. Локальное
   обрезание не используется, курсор и snapshot ID не выдумываются. Даже при
   работающем offset меняющийся аукцион допускает пересечения и пропуски.
2. **Отсутствие выкупа:** в просмотренных production-лотах buyoutPrice > 0;
   наблюдений отсутствия выкупа нет. Ранее согласованное `0 → null` реализовано
   и проверено контрольным ответом. Оно остаётся допущением, а не установленным
   production-правилом. Отсутствующее/нечисловое обязательное buyoutPrice не
   превращается в ноль: это ошибка формата источника.
3. В OpenAPI и прочитанных подготовительных материалах численный интервал
   лимитов не указан. В живых ответах появились `X-Ratelimit-Limit=60` у OAuth,
   `x-ratelimit-limit=400`, `remaining`, `reset` у аукциона. Наблюдаемый reset —
   Unix milliseconds. Число в limit не выдаётся за лимит «в секунду/минуту».
   Остаток 0 блокирует новые обращения до reset; неизвестное время даёт только
   локальную задержку, без выдуманного Retry-After. Настоящий 429 не провоцировался.

## Собственный API

`GET /api/items/{id}/lots?offset=0&limit=20`

- ID — точное регистрозависимое совпадение с локальным справочником, иначе 404.
- offset: 0–2147483647; limit: 1–200, по умолчанию 0/20. Неверные значения и
  повторения параметров → 400 с `{code, message, fieldErrors}`.
- Ответ: `{items, offset, limit, nextOffset, hasMore, totalCount, fetchedAt,
  source, pageId}`. `nextOffset` nullable, пустая исходная страница останавливает
  продолжение даже при противоречивом total. Достижение границы Int32 также
  останавливает продолжение. total — счётчик в момент ответа, не снимок аукциона.
- AuctionLot: `{id, itemId, quantity, startPrice, currentPrice, buyoutPrice,
  startTime, endTime}`. Цены — строки; nullable currentPrice/buyoutPrice.
  На backend числовые цены читаются как decimal, проверяются на неотрицательный
  целый Int64 и форматируются InvariantCulture. Никаких вычислений цен через
  JavaScript Number; отображение целых цен через BigInt.
- Выкуп за штуку вычисляется только на клиенте из buyoutPrice / quantity;
  нового внешнего поля или backend-запроса нет. Фильтрация и сортировка используют
  точные отношения BigInt (перекрёстное умножение), отображение округляется
  до двух знаков с `≈` при потере дробных знаков. Оба диапазона выкупа работают
  одновременно по загруженным страницам и не влияют на nextOffset.
- startTime/endTime/fetchedAt — ISO UTC с `Z`; окончание показывается явно в UTC.
- id=`{pageId}:{rowIndex}` — временный внутренний ключ. Кэш возвращает тот же
  pageId и исходный fetchedAt; новая страница источника получает новый pageId.
- Клиент не добавляет уже принятую страницу (pageId или offset). Одинаковые
  поля разных страниц не склеиваются. Точная межстраничная дедупликация не
  гарантируется. Подробности доступны только из текущего набора в памяти;
  после его потери временный URL не инициирует выдуманный внешний запрос лота.
- HTTP `Cache-Control: no-store`: промежуточный/браузерный кэш не подменяет
  управляемый серверный кэш и ручное обновление.

Ошибки собственного API, без сырых тел/заголовков авторизации:

| HTTP | code | Значение |
| --- | --- | --- |
| 400 | invalid_parameters | Неверная пагинация |
| 404 | item_not_found | Предмета нет в справочнике |
| 429 | source_rate_limited | 429 источника или исчерпанный объявленный остаток |
| 502 | source_unavailable | HTTP/сетевая ошибка источника |
| 502 | source_auth_failed | OAuth/доступ источника отклонён |
| 502 | invalid_source_response | Некорректный JSON/обязательные данные |
| 503 | source_not_configured | Нет серверных реквизитов |
| 503 | server_busy | Достигнут локальный предел ожидающих страниц |
| 504 | source_timeout | Истекло время ожидания источника/общей очереди |

Тело: `{code, message}`. Известный Retry-After источника (секунды или HTTP-date)
преобразуется в оставшиеся секунды; время не перезапускается при чтении кэша.
Для ошибки 5xx с Retry-After он также передаётся и ограничивает новые обращения.

## Память, частота и отмена

- Один AuctionTransport, общий SemaphoreSlim для всех исходящих запросов,
  включая OAuth. Не более одного активного HTTP-запроса; промежуток между
  началами не меньше MinimumRequestIntervalMs (по умолчанию 1000).
- Тайм-аут одной попытки, включая ожидание общего ограничителя и чтение тела:
  RequestTimeoutSeconds=15. Редиректы отключены. HttpClient переиспользуется.
- Токен в памяти, раннее обновление за min(60 сек, 10% срока). Параллельные
  запросы токена объединены семафором. Только после HTTP 401 разрешён один
  повтор OAuth и один повтор лотов; параллельные 401 могут использовать уже
  обновлённый токен. После повторного 401 токен отклоняется. 403 не запускает
  повторную авторизацию. Бесконечных/автоматических повторов нет.
- Кэш страниц общий на backend, ключ `(точный id, offset, limit)`, TTL 10 сек,
  максимум 256 страниц, одинаковые незавершённые запросы объединяются.
  Ошибки кратко запоминаются на 2 сек либо до известного Retry-After;
  обновление кэша не меняет время получения от источника.
- Максимум 16 разных ожидающих страниц; значения настраиваются в appsettings.
  Истёкшие записи удаляются при обращении, фоновых очистителей/опросов нет.
- Отмена браузера прекращает его ожидание, но не срывает общий запрос другим
  посетителям; запрос ограничен серверным тайм-аутом и остановкой приложения.
- Frontend ограничивает ожидание всей цепочки 65 сек (включая OAuth и один
  допустимый повтор), блокирует повторные клики синхронным флагом, игнорирует
  запоздалые ответы. При смене предмета набор сбрасывается.
- «Обновить» начинает новый набор с offset=0 после успеха; может получить ещё
  свежую кэшированную страницу с прежним временем. При неудаче старые данные
  сохраняются с явной отметкой. Retry-After только включает ручные кнопки после
  указанного срока, не запускает автоматический повтор.

Реквизиты — только appsettings.Local.json / серверное окружение. Локальный файл
не отслеживается Git и не копируется в build/publish. Backend не журналирует
тела OAuth, токены или исходные диагностические ответы. Лоты постоянно не хранятся.

## Воспроизводимые проверки

Из корня, после сборки backend:

```sh
node --test scripts/search.test.mjs scripts/lots.test.mjs
```

11 тестов лотов используют **подменённый локальный HTTP-источник**, 5 тестов
поиска — локальный индекс. Настоящий HTTP handler backend выполняет запросы к
контрольному серверу; проверены Int64, UTC, nullable-поля, overfull/empty страницы,
валидация, single-flight, отмена ожидания, TTL, общий ограничитель/очередь,
OAuth/401/403 и истечение токена, 429 (delta/date/без Retry-After), reset и 504.
Эти тесты не проверяют живой API. Живой результат и ручной чек-лист отдельно
зафиксированы в журнале ИИ.
